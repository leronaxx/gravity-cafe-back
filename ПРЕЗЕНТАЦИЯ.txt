== ЧТО ЭТО ВООБЩЕ ==

Это сайт кафе, как у настоящих ресторанов. Что он умеет:
  - Показывать меню (напитки, десерты, основные блюда)
  - Добавлять блюда в корзину и оформлять предзаказ
  - Бронировать столик (выбор зоны: зал / терраса / улица)
  - Регистрация и вход пользователей
  - Личный кабинет с историей заказов и бронирований

Сайт состоит из 5 страниц: главная, меню, бронирование,
о нас, профиль.


== ИЗ ЧЕГО СОСТОИТ ПРОЕКТ (3 ГЛАВНЫЕ ЧАСТИ) ==

1) ФРОНТЕНД — то, что видит пользователь в браузере.
   Это HTML-страницы + оформление (CSS) + скрипты (JavaScript).
   Когда открываешь сайт — ты видишь именно его.

2) БЭКЕНД (сервер) — программа, которая работает "за кулисами".
   Она принимает запросы от сайта ("дай меню", "создай заказ")
   и отвечает на них. Работает на Node.js + Express.

3) БАЗА ДАННЫХ — PostgreSQL. Здесь лежит ВСЁ:
   меню, картинки блюд, пользователи, заказы, бронирования,
   настройки кафе (адрес, телефон, часы работы).


== КАК ОНИ ОБЩАЮТСЯ МЕЖДУ СОБОЙ ==

Пользователь (браузер)
       ↓  (кликает "Добавить в корзину")
   ФРОНТЕНД
       ↓  (шлёт запрос "дай меню")
   БЭКЕНД (Express)
       ↓  (выполняет SQL-запрос)
   БАЗА ДАННЫХ (PostgreSQL)
       ↓  (возвращает данные)
   БЭКЕНД
       ↓  (возвращает в виде JSON)
   ФРОНТЕНД
       ↓  (рисует карточки на странице)
   Пользователь видит результат


== КЛЮЧЕВЫЕ ТЕХНОЛОГИИ (что сказать если спросят) ==

- HTML / CSS / JavaScript — стандартный набор для сайтов.
- Vite — сборщик проекта. Запускает сайт при разработке
  и упаковывает его для публикации.
- Node.js — среда, в которой работает сервер.
- Express.js — библиотека, которая упрощает создание сервера
  (обрабатывает маршруты типа /api/menu, /api/orders).
- PostgreSQL — серьёзная база данных (ею пользуются банки,
  Instagram, Spotify и др.).
- JWT (JSON Web Token) — технология авторизации. После входа
  пользователь получает "токен" — как электронный пропуск,
  который он предъявляет при каждом запросе.
- bcrypt — библиотека для шифрования паролей. Пароли никогда
  не хранятся в открытом виде, только "хэш" (отпечаток).

== КАК РАБОТАЕТ АВТОРИЗАЦИЯ (спросят — расскажи так) ==

1. Пользователь вводит имя/телефон/пароль и жмёт "Регистрация".
2. Сервер шифрует пароль (bcrypt) и сохраняет в таблицу users.
3. Сервер выдаёт токен (JWT) — похож на электронный билет.
4. Браузер сохраняет токен в localStorage.
5. Теперь при каждом запросе (заказ, бронь) браузер прикладывает
   этот токен в заголовке Authorization.
6. Сервер проверяет токен и понимает: "ага, это Иван, его id=5".
7. Заказ записывается с привязкой к этому пользователю.
8. При следующем входе пользователь видит в личном кабинете
   свои прошлые заказы и брони.


== ПОЧЕМУ ТАК МНОГО ФАЙЛОВ (если спросят) ==

Разделение по ответственности:
- Фронт НЕ лазит в БД напрямую (это небезопасно).
- Фронт спрашивает у сервера через API ("/api/menu", "/api/orders").
- Сервер — единственный, кто умеет работать с БД.
- Каждый файл в routes/ отвечает за одну "зону" сайта.
  Так проще поддерживать.


== КАК ЗАПУСТИТЬ НА КОМПЬЮТЕРЕ (если попросят показать) ==

1. Установить PostgreSQL и Node.js
2. Создать базу: createdb gravity_cafe
3. В папке server: npm install
4. В корне проекта: npm install
5. Наполнить БД: cd server && npm run seed
6. Запустить сервер: npm start
7. В другом терминале: npm run dev
8. Открыть http://localhost:5173 в браузере

== ЧАСТЫЕ ВОПРОСЫ ОТ ПРЕПОДА И ОТВЕТЫ ==

В: Почему выбрали именно эти технологии?
О: Node.js + Express — стандарт для бэкенда на JavaScript,
   простой и быстрый. PostgreSQL — надёжная СУБД с поддержкой
   всех нужных типов данных (включая бинарные для картинок).
   Vite — современный сборщик, работает быстрее вебпака.

В: Почему картинки в БД, а не в файлах?
О: По требованию задачи — "всю статику перенести в БД".
   Плюс: проще деплоить (одна БД = всё на месте), нельзя
   случайно удалить файл. Минус: немного медленнее, но для
   маленького сайта это незаметно (есть кеширование 24ч).

В: Как защитили пароли?
О: Хэшированием через bcrypt с 10 раундами соли. В БД
   никогда не лежит настоящий пароль — только хэш, по которому
   невозможно восстановить исходный пароль.

В: Что такое JWT?
О: Токен с "подписью" сервера. При входе сервер создаёт
   токен с данными пользователя и подписывает его секретом.
   Клиент прикладывает этот токен к запросам. Сервер проверяет
   подпись — если валидна, пускает. Токен живёт 7 дней.

В: Что если сервер упадёт?
О: Сайт не будет работать — появится сообщение об ошибке.
   Но данные в БД сохранены и не потеряются. При перезапуске
   сервера всё восстановится.

В: Чем отличается GET от POST?
О: GET — "прочитать данные" (меню, заказы). POST — "создать
   или изменить" (зарегистрироваться, оформить заказ).

В: Что будет если пользователь не залогинен и попробует
   оформить заказ?
О: Сервер вернёт ошибку 401 (Unauthorized). Фронт это
   перехватит и покажет окно с просьбой войти или
   зарегистрироваться.

== ГЛАВНАЯ ИДЕЯ (это надо сказать обязательно) ==

Обычная нейросеть отвечает "по памяти" и может выдумать блюдо,
которого нет, или назвать неверную цену. Это называется
"галлюцинации".

Мы сделали иначе — две вещи:

  1) RAG (Retrieval-Augmented Generation, "генерация с опорой
     на найденные данные"):
     сначала программа ищет в базе знаний кафе подходящие факты,
     и только потом отдаёт их нейросети вместе с вопросом.
     Нейросеть отвечает, опираясь на эти факты.

  2) Function calling ("вызов инструментов"):
     точные данные (цена, калории, БЖУ, аллергены) нейросеть
     не вспоминает, а ЗАПРАШИВАЕТ у программы. Программа идёт
     в базу данных PostgreSQL, делает SQL-запрос и возвращает
     точный ответ.

Простая аналогия: официант не придумывает цены по памяти, а
смотрит в блокнот и в кассу. Примерно так же работает ассистент.

== ЧТО ГОВОРИТЬ, ЕСЛИ СПРОСЯТ ==

"Почему RAG, а не обучение своей модели?"
  — Обучение требует тысяч примеров и денег. RAG даёт точность
    на наших данных без обучения: мы просто подкладываем нужные
    факты в запрос к модели.

"Что если интернет пропадёт?"
  — Ассистент продолжит работать: если облачная модель недоступна,
    включается режим поиска по базе знаний. Сайт не ломается.

"Сколько это стоит?"
  — С локальной моделью Ollama — ноль рублей, всё работает
    на компьютере. С облачной моделью — копейки за диалог,
    плюс стоит ограничение 20 запросов в минуту.

"Как боретесь с выдуманными фактами?"
  — Три уровня: (1) в промпте запрещено выдумывать и велено
    использовать только переданные данные; (2) точные цифры
    берутся только через SQL-запросы; (3) если данных нет —
    ассистент честно говорит об этом и предлагает позвонить.

"Как защищены данные?"
  — Ассистент не спрашивает и не хранит персональные данные
    гостей. Он ограничен темой кафе: на посторонние вопросы
    вежливо отказывается отвечать.
