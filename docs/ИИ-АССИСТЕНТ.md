# ИИ-ассистент Gravity Café — техническая документация

Документ описывает, что именно добавлено в проект, как это работает и как это
запустить. Материалы для защиты диплома — в файлах
[ЗАЩИТА-ИИ-АССИСТЕНТ.md](ЗАЩИТА-ИИ-АССИСТЕНТ.md) (шпаргалка и вопросы комиссии)
и [ГЛАВА-ДИПЛОМА-ИИ-АССИСТЕНТ.md](ГЛАВА-ДИПЛОМА-ИИ-АССИСТЕНТ.md) (черновик главы).

## 1. Что умеет ассистент

| Возможность | Пример вопроса гостя |
|---|---|
| Подбор блюд и напитков | «Что посоветуете к кофе?», «Помогите выбрать десерт» |
| Калорийность и КБЖУ | «Сколько калорий в тирамису?» |
| Подбор под ограничения | «Есть ли блюда до 300 ккал?», «Что до 400 рублей?» |
| Вегетарианские позиции | «Какие у вас вегетарианские блюда?» |
| Аллергены | «У меня аллергия на орехи, что можно взять?» |
| Адрес и как добраться | «По какому адресу вы находитесь?» |
| Часы работы и контакты | «До скольки вы работаете в выходные?» |
| История и концепция кафе | «Расскажите историю вашего кафе» |
| Бронирование и предзаказ | «Как забронировать столик на террасе?» |
| Бытовые вопросы | «У вас есть Wi-Fi?», «Можно с собакой?» |
| Посторонние темы | Вежливый отказ: ассистент отвечает только про кафе |

Ассистент **не** оформляет заказ и не оплачивает его за гостя, **не** даёт
медицинских рекомендаций и **не** выдумывает блюда: все цены, калории и факты
он берёт из базы данных сайта и из базы знаний.

## 2. Быстрый старт

### Шаг 1. Обновить базу данных

К существующей базе применяется миграция (данные не теряются):

```bash
cd server
psql -U postgres -d gravity_cafe -f seed/migrations/001_assistant.sql
```

Миграция добавляет в `menu_items` поля `calories`, `proteins`, `fats`, `carbs`,
`is_vegetarian`, `allergens`, заполняет их для 18 позиций меню и создаёт таблицы
`assistant_messages` и `assistant_feedback` для логов диалогов.

> Если база создаётся с нуля, достаточно `schema.sql` + `npm run seed` —
> новые поля уже включены в них.

### Шаг 2. Настроить окружение

```bash
cd server
cp .env.example .env         # или создайте .env вручную
```

Минимально нужно указать доступ к PostgreSQL. Дальше — выбор языковой модели
(см. раздел 5): либо локальная Ollama, либо облачный API, либо ничего
(ассистент будет работать в режиме поиска по базе знаний).

### Шаг 3. Запустить сервер

```bash
cd server
npm install
npm start
```

Проверка, что ассистент жив:

```bash
curl http://localhost:3000/api/assistant/health
```

### Шаг 4. Открыть сайт

* `gravity-cafe-front` — открыть `index.html` (или поднять статический сервер).
* `gravity-cafe-back` — `npm run dev` (Vite поднимет сайт и проксирует `/api` на `:3000`).

В правом нижнем углу появится кнопка **«Спросить ИИ»**.

## 3. Архитектура

```
                    ГОСТЬ (браузер)
                          │  вопрос + контекст (страница, корзина)
                          ▼
        ┌──────────────────────────────────────────────┐
        │  ЧАТ-ВИДЖЕТ  ai-assistant.js / ai-assistant.css │
        │  • панель чата, подсказки, история диалога     │
        │  • чтение потока SSE и печать ответа по частям │
        │  • экранирование HTML (защита от XSS)          │
        └───────────────────────┬──────────────────────┘
                                │ POST /api/assistant/chat/stream
                                ▼
        ┌──────────────────────────────────────────────┐
        │  EXPRESS  routes/assistant.js                 │
        │  • валидация запроса, rate limit (20/мин)     │
        │  • SSE-поток, отмена при уходе гостя          │
        └───────────────────────┬──────────────────────┘
                                ▼
        ┌──────────────────────────────────────────────┐
        │  АГЕНТ  assistant/agent.js                    │
        │   1. RAG-поиск по базе знаний (retriever.js)  │
        │   2. Снимок меню из PostgreSQL                │
        │   3. Системный промпт (prompt.js)             │
        │   4. Цикл вызова инструментов (tools.js)      │
        │   5. Логирование диалога (logger.js)          │
        └───────┬───────────────────────┬──────────────┘
                ▼                       ▼
   ┌─────────────────────┐   ┌──────────────────────────┐
   │ ПРОВАЙДЕР LLM        │   │ PostgreSQL               │
   │ providers.js:        │   │ • menu_items  (меню, КБЖУ)│
   │  ollama (локально)   │   │ • cafe_settings (адрес,   │
   │  openai (облако)     │   │   часы, история)          │
   │  mock (без модели)   │   │ • assistant_messages      │
   └─────────────────────┘   └──────────────────────────┘
```

Три идеи, на которых держится решение:

1. **RAG (Retrieval-Augmented Generation).** Прежде чем спросить языковую
   модель, мы ищем в базе знаний подходящие факты и подставляем их в промпт.
   Модель отвечает, опираясь на эти факты, а не на свои общие знания.
2. **Function calling.** Точные данные (цены, калории, БЖУ, аллергены) модель
   не «вспоминает», а запрашивает инструментами, которые выполняют SQL-запросы.
   Это исключает выдуманные блюда и устаревшие цены.
3. **Резервный режим.** Если языковая модель недоступна, ассистент отвечает
   детерминированным поиском по базе знаний и данным из БД. Сайт продолжает
   работать, ответ помечается флагом `degraded`.

## 4. Как проходит один вопрос

1. Гость пишет вопрос → виджет собирает `message`, историю диалога (до 10 реплик)
   и контекст (страница, состав корзины).
2. `POST /api/assistant/chat/stream` проверяет длину сообщения и лимит частоты.
3. Ретривер токенизирует вопрос (нижний регистр, ё→е, удаление стоп-слов,
   отрезание русских окончаний) и ищет top-4 факта по косинусной близости
   TF-IDF-векторов.
4. Агент берёт из PostgreSQL снимок меню (18 позиций с ценами и калориями,
   кэш на 30 секунд) и собирает системный промпт.
5. Модель получает промпт, историю и описание 5 инструментов.
6. Если модель просит данные — агент выполняет инструмент (SQL) и возвращает
   результат модели; цикл повторяется, но не более 4 раз.
7. Финальный текст уходит гостю потоком (SSE), виджет печатает его постепенно.
8. Диалог записывается в `assistant_messages`, гость может поставить 👍 или 👎.

## 4.1. Гибридная маршрутизация: когда модель вообще не нужна

Не каждый вопрос стоит отправлять в языковую модель. Ответы про калорийность,
состав, аллергены, цены, адрес и часы работы обязаны быть точными, а небольшие
локальные модели (3–7 млрд параметров) иногда путают факты: например, на живом
прогоне `qwen2.5:3b-instruct` назвала вегетарианские блюда «не содержащими
молока», хотя в тирамису молоко есть. Цена такой ошибки в вопросе об аллергенах
слишком высока — это здоровье гостя.

Поэтому в проекте работает **гибридная маршрутизация** (`ASSISTANT_ROUTING=hybrid`,
режим по умолчанию):

| Тип вопроса | Кто отвечает | Время ответа |
|---|---|---|
| Калории, БЖУ, состав, аллергены, вегетарианские блюда | детерминированный поиск по PostgreSQL | ~0,01 с |
| Цены, подбор «до N ₽ / до N ккал», обзор меню, популярное | детерминированный поиск по PostgreSQL | ~0,01 с |
| Адрес, часы работы, телефон, бронирование, удобства | база знаний + `cafe_settings` | ~0,01 с |
| Рекомендации, история кафе, общие вопросы | языковая модель с RAG и инструментами | 5–25 с локально |

Маршрут определяется лексическим анализатором намерений (`detectIntent` в
`fallback.js`) до обращения к модели. Решение осознанное: детерминированный
поиск не может выдумать цифру, работает мгновенно и не требует ресурсов, а
языковая модель подключается там, где действительно нужен живой текст.

Значение `ASSISTANT_ROUTING=llm` заставляет отправлять в модель все запросы —
это удобно, чтобы показать «чистый» RAG-конвейер на защите. В обоих режимах
ассистент вызывает одни и те же инструменты к базе данных, а в ответе есть поле
`route` (`deterministic` или `llm`), по которому видно, кто подготовил ответ.

## 5. Выбор языковой модели

Провайдер переключается одной строкой в `.env` — код не меняется.

| Провайдер | Значение `ASSISTANT_PROVIDER` | Плюсы | Минусы |
|---|---|---|---|
| Ollama (локально) | `ollama` | бесплатно, офлайн, данные не покидают компьютер | нужен мощный ноутбук, качество ниже облака |
| Облачный API | `openai` | лучшее качество, не нужен мощный ПК | нужен ключ, платно, нужен интернет |
| Только база знаний | `mock` | работает всегда и мгновенно | нет «живой» речи, ответы шаблонные |
| Автовыбор | `auto` | сам найдёт доступный вариант | — |

Установка локальной модели:

```bash
# 1. Установить Ollama: https://ollama.com
# 2. Скачать модель (~4.7 ГБ)
ollama pull qwen2.5:7b-instruct
# 3. В .env указать
ASSISTANT_PROVIDER=ollama
OLLAMA_MODEL=qwen2.5:7b-instruct
```

Подключение облачного OpenAI-совместимого API (OpenAI, DeepSeek, OpenRouter):

```bash
ASSISTANT_PROVIDER=openai
OPENAI_BASE_URL=https://api.deepseek.com/v1
OPENAI_API_KEY=sk-...
OPENAI_MODEL=deepseek-chat
```

Один и тот же адаптер работает с любым сервисом, совместимым с OpenAI API:
различаются только базовый URL, ключ и имя модели.

## 6. Инструменты ассистента (function calling)

| Инструмент | Что делает | Аргументы |
|---|---|---|
| `search_menu` | поиск блюд с фильтрами | `query`, `category`, `max_price`, `max_calories`, `min_proteins`, `vegetarian_only`, `exclude_allergens`, `sort_by`, `limit` |
| `get_menu_item` | карточка блюда: состав, цена, КБЖУ, аллергены | `name` |
| `get_cafe_info` | адрес, телефон, почта, часы работы, история | `topic` |
| `search_cafe_knowledge` | поиск по базе знаний о кафе | `query` |
| `get_popular_items` | популярные позиции по фактическим заказам | `limit` |

Все фильтры выполняются параметризованными SQL-запросами: значения передаются
отдельно от текста запроса, поэтому SQL-инъекция через аргументы модели
невозможна. Значение `sort_by` сверяется со словарём допустимых сортировок.

## 7. База знаний

`server/assistant/knowledge-base.json` — 37 фактов (chunks). Каждый факт:

```json
{
  "id": "history-origin",
  "topic": "history",
  "title": "История появления Gravity Café",
  "tags": ["история", "открытие", "основание"],
  "text": "Gravity Café открылось в 2025 году..."
}
```

Темы: `history`, `location`, `hours`, `contacts`, `menu`, `nutrition`,
`ordering`, `reservation`, `payment`, `amenities`, `atmosphere`, `services`,
`site`, `assistant`.

База знаний лежит в виде данных, а не кода: чтобы добавить новый факт,
достаточно дописать объект в JSON — пересборка проекта не нужна. Динамические
данные (адрес, телефон, часы работы, текст «о кафе») берутся из таблицы
`cafe_settings`, поэтому изменение настроек кафе сразу отражается в ответах.

Поиск — лексический (TF-IDF + косинусная близость). Векторные эмбеддинги
сознательно не используются: они требуют внешнего API или дополнительной
модели, а на объёме в несколько десятков фактов лексический поиск даёт
сопоставимое качество при нулевых затратах. При росте базы знаний эмбеддинги
можно добавить вторым каналом поиска — код ретривера к этому готов.

## 8. Ограничения и безопасность

| Механизм | Значение / описание |
|---|---|
| Тематика | системный промпт: только кафе, посторонние вопросы отклоняются вежливо |
| Запрет галлюцинаций | «используй только данные ниже»; при отсутствии данных — предложить позвонить |
| Медицина | ассистент не диетолог: КБЖУ справочно, без рекомендаций |
| Аллергии | обязательное предупреждение, что блюда готовятся на одной кухне |
| Длина сообщения | 1000 символов |
| Частота запросов | 20 запросов в минуту на IP (`X-RateLimit-*`, ответ 429) |
| Шаги агента | не более 4 итераций вызова инструментов (защита от зацикливания) |
| SQL | параметризованные запросы, белый список сортировок |
| XSS | ответ экранируется перед вставкой в DOM (проверено тестом) |
| Персональные данные | ассистент не запрашивает и не хранит ФИО и телефоны гостей |
| Отмена | генерация прерывается, если гость закрыл вкладку |

## 9. HTTP API

| Метод | Адрес | Назначение |
|---|---|---|
| POST | `/api/assistant/chat` | ответ одним JSON (без стриминга) |
| POST | `/api/assistant/chat/stream` | ответ потоком, Server-Sent Events |
| POST | `/api/assistant/feedback` | оценка ответа: `rating` = 1 или −1 |
| GET | `/api/assistant/health` | какой провайдер доступен, сколько фактов и блюд |
| GET | `/api/assistant/stats?days=7` | статистика диалогов |
| GET | `/api/assistant/suggestions` | подсказки-кнопки для чата |
| GET | `/api/assistant/knowledge` | оглавление базы знаний |
| GET | `/api/assistant/tools` | описание инструментов (отладка) |
| POST | `/api/assistant/refresh` | сбросить кэш меню после правок |

### Пример: обычный запрос

```bash
curl -X POST http://localhost:3000/api/assistant/chat \
  -H 'Content-Type: application/json' \
  -d '{"message":"Сколько калорий в тирамису?","sessionId":"demo-1"}'
```

```json
{
  "reply": "**Тирамису** (десерты)\n\nЦена: **450 ₽**\nКалорийность: **420 ккал** на порцию\nБЖУ: белки 7 г, жиры 26 г, углеводы 38 г\n...",
  "sources": [{"id": "nutrition-general", "title": "Калорийность и КБЖУ блюд", "score": 0.284}],
  "toolCalls": [{"name": "get_menu_item", "arguments": {"name": "Тирамису"}}],
  "provider": "mock",
  "degraded": true,
  "latencyMs": 12,
  "messageId": 42
}
```

### Пример: потоковый запрос (как это делает виджет)

```bash
curl -N -X POST http://localhost:3000/api/assistant/chat/stream \
  -H 'Content-Type: application/json' \
  -d '{"message":"По какому адресу вы находитесь?","sessionId":"demo-2"}'
```

```
data: {"type":"meta","provider":"mock","degraded":true,"sources":[...]}

data: {"type":"delta","text":"Мы находимся по адресу: "}

data: {"type":"done","reply":"Мы находимся по адресу: **Ростов-На-Дону, ул. Пушкинская, 151**...","toolCalls":[{"name":"get_cafe_info"}],"messageId":43}
```

Типы событий: `meta` (провайдер и источники), `delta` (порция текста),
`reset` (очистить черновик — модель ушла за данными), `tool` (вызван инструмент),
`done` (итог), `error`.

### Отладочный режим виджета

Под каждым ответом виджет показывает чипы с источниками («📚 Адрес кафе»).
Дополнительно в отладочном режиме он показывает, какие инструменты вызывала
модель («🔧 get_menu_item»). Этот режим включается автоматически на `localhost`
и `127.0.0.1` — удобно для демонстрации на защите. На другом адресе его можно
включить явно, до подключения скрипта виджета:

```html
<script>window.GRAVITY_ASSISTANT_DEBUG = true;</script>
```

## 10. Логирование и метрики

| Таблица | Что хранит |
|---|---|
| `assistant_messages` | каждое сообщение: роль, текст, провайдер, модель, задержка, токены, флаг `degraded`, использованные источники и инструменты (JSONB) |
| `assistant_feedback` | оценки гостей: `rating` = 1 / −1 и комментарий |

```bash
curl http://localhost:3000/api/assistant/stats?days=7
```

Возвращает: количество вопросов и ответов, число сессий, среднюю задержку и
p95, долю ответов без языковой модели, расход токенов, распределение по
провайдерам, частоту вызова каждого инструмента, самые востребованные темы
базы знаний, количество 👍/👎 и активность по дням.

Эти метрики — основа для главы диплома об оценке результатов и для развития
проекта: вопросы, на которые ассистент не нашёл ответ, показывают, какие факты
стоит добавить в базу знаний.

## 11. Тестирование

### Юнит-тесты (без базы данных и без языковой модели)

```bash
cd server
npm test
```

37 тестов: ретривер (поиск адреса, калорий, вегетарианских позиций, отсутствие
ложных срабатываний), построение SQL и защита от инъекций, разбор ответов

Отдельный файл `tests/agent-openai.test.mjs` поднимает локальный HTTP-сервер,
который притворяется OpenAI API, и проверяет полный цикл function calling:
модель просит инструмент → агент выполняет SQL → результат возвращается
модели → модель даёт финальный ответ. Тот же тест проверяет потоковый режим
и защиту от зацикливания.

### Интеграционные тесты на живой PostgreSQL

```bash
cd server
npm run test:db
```

34 проверки: фильтры «до 300 ккал», «только вегетарианское», «без орехов»,
«много белка», «до 300 рублей» — на реальных данных; корректность КБЖУ;

и расчёт статистики. Если база недоступна, скрипт печатает инструкцию и
завершается без ошибки.

### Проверка виджета в браузерном окружении

```bash
cd server
npm run test:widget     # нужен запущенный бэкенд: npm start
```

Скрипты лежат в `server/tests/widget/`; используется jsdom — браузер без
графического интерфейса, поэтому настоящий Chrome не нужен. Всего 59 проверок
в трёх наборах.

Виджет проверяется в DOM-окружении с реальными запросами к серверу:
построение интерфейса, открытие панели, загрузка подсказок и статуса модели,
потоковый ответ, показ источников, кнопки оценки, сохранение истории,
сброс диалога, а также защита от XSS (вредоносный текст в ответе остаётся
текстом, теги не создаются, скрипт не выполняется). Отдельно проверены
реальные HTML-страницы сайта: виджет инициализируется на всех страницах,
скрипты сайта не ломаются, корзина передаётся ассистенту.

## 13. Направления развития

* **Эмбеддинги вместо TF-IDF** — гибридный поиск (лексический + векторный)
  для больших баз знаний и синонимов.
* **Голосовой ввод** — Web Speech API в виджете.
* **Рекомендации на основе истории заказов** — персональные подсказки
  постоянным гостям.
* **Админ-панель аналитики** — визуализация `/api/assistant/stats`.
* **Redis для rate limit** — корректная работа при нескольких серверах.
* **Оформление заказа через диалог** — инструмент, создающий черновик заказа
  (сейчас ассистент только объясняет, как оформить заказ, и это осознанное
  ограничение безопасности).
